# v4.1 — v4 flow on a packed, fast training loader

v4.1 trains the **same model** as v4: the six targets, the frozen v2 regression,
calibration, the loss, validation, the effective batch of 64 and 512 optimizer
steps per epoch are all unchanged. Only the training data path and the job's
CPU/memory request are different. The run starts from scratch in
`runs/merraflow_v4_1`.

## Why v4 was slow

The v4 epoch log (epoch 7: 2257 s data wait + 4115 s "step" per rank, about
106 min for 1024 batches of 8) shows the GPUs doing about 0.2 s of work per
batch and waiting about 6 s. The "step" time includes waiting in the DDP
all-reduce for ranks whose loaders are behind.

For every sample, v4 cropped a **576×576 broad context** from three
full-resolution memory maps: the condition, the baseline and the
previous-hour condition. That is about 23 MB of strided GPFS page faults. For
most origins the window crosses the 1059×1799 grid edge, so the crop falls
back to element-wise fancy indexing. The context was then area-averaged 6× down
to 96×96. Each sample also opened about 8 files for a random hour, with a
16-entry map cache that almost never hit.

The v4 job requested 16 of the node's 48 cores and 128 GB of its 488 GB.

## What v4.1 changes

| | v4 | v4.1 |
|---|---|---|
| Broad context | rebuilt from 576² crops and pooled for every sample | pooled once per hour during packing; a 96² read |
| Local 192² fields | 7 memory-mapped `.npy` files per hour | 1 tiled file per hour; about 7 contiguous reads per section |
| Proposal scores | per-worker cache, one file per hour | one shared memory-mapped table |
| Loader workers | 4 per rank, restarted every epoch | 10 per rank, persistent (the epoch is encoded in the index) |
| Batch | 8 × accumulate 2 | 16 × accumulate 1 (same effective batch of 64) |
| Job | 16 cores, 128 GB | 48 cores, 440 GB (the whole node) |
| Candidate origins | stride 32 | stride 24 (multiples of the pooling factor 6) |

Measured at production size (1059×1799, one CPU thread, data already in the
page cache): building one v4.1 sample takes **5.8 ms**. Building just v4's
inputs from arrays already in RAM, with no I/O at all, takes **80 ms**. On
GPFS, v4.1 reads about 5 MB in about 30 contiguous reads per sample. v4
touched about 23 MB through about 15k page faults.

## Exactness

Candidate origins lie on multiples of `f = (size+2·halo)·context_scale /
context_size` (6). For those origins, the pooled blocks are exactly the blocks
v4 averaged, including the replicated pixels outside the domain. Every tensor
of a v4.1 sample is **bit-identical** to v4's `DatasetV4` sample for the same
hour and origin. `tests/test_v4_1.py` checks this through the real
`DatasetV4`, at edge and interior origins. The data preflight checks it again
on real data.

Because the inputs are defined identically, v4.1 checkpoints run through the
unchanged v4 full-domain inference: `cli_v4_1 predict`.

The only change in what the model sees during training: the last origin on each
axis snaps down to a multiple of 6. At most 5 edge rows or columns move from a
patch's interior into its halo, and they are still supervised because
`loss_on_halo` is on.

## Storage and run time

`cli_v4_1 plan-packed` prints the exact numbers. For the production
geometry, each packed hour is 139 MB:

- 6 raw predictors + 11 baseline/truth channels, tiled 32×32, about 135 MB
- the pooled context, 4.3 MB
- the proposal scores, 23 KB

That is about **1.4 TB** for the roughly 10k train/val hours plus their history
hours. Packing takes about 3–4 s of CPU per hour, so about an hour per month.
The monthly array tasks run 8 at a time by default. Packing is restart-safe:
resubmit and it skips finished hours.

## Startup is minimal

Training jobs run **no preflight**. The packing finalizer runs the data
checks once, on a CPU node:

- manifest checks
- the regression checkpoint check
- real-data equality with v4 for a few samples

At train start, each rank:

1. reads the JSON manifests;
2. memory-maps the static fields (nothing large is pickled into the workers;
   each dataset pickle is a few MB);
3. starts its 10 persistent workers **once**;
4. calibrates on the first 64 batches **through those same workers**, then
   continues straight into epoch 1.

Resumed jobs skip calibration entirely.

## Validation, plots and checkpoints (every 5 epochs)

Metrics are v4's: CRPS, MAE against the coarse input and the regression,
ensemble-mean RMSE, spread and rain occurrence, over the 256 uniform
validation patches. Precipitation CRPS still selects `best_v4_1.pt`. Each
validation writes `validation_plots/epoch_NNNN/`:

- `rain_patch_K.png`: rain maps for **fixed rainy validation patches**:
  coarse input, frozen regression, truth, 4 members, ensemble mean,
  P(≥ 1 mm/h) with the observed contour, and spread. The patches are chosen
  once and saved in `preview_patches.json`. The choice ranks the input-rain-richest
  origin of each validation hour by observed rain, keeping patches at least
  12 h apart. Fixed noise means epochs can be compared directly.
- `states_patch_K.png`: t2m, ps, u10m, v10m and q2m for the same patches:
  coarse, truth, ensemble mean, mean − truth (with RMSE against the coarse
  input's) and spread.
- `diagnostics.png`: over all validation patches: rain-intensity
  distribution (truth, flow, regression, coarse), rank histograms for all six
  variables, and radial power spectra.
- `history.png`: loss and learning rate, CRPS/coarse-MAE skill, rain
  occurrence, throughput, per-variable curves, and spread/RMSE.
- `metrics.json` and `samples.npz`.

Checkpoints: `last_v4_1.pt` every epoch, `best_v4_1.pt` on improvement, and
`checkpoints/epoch_NNNN_v4_1.pt` every `checkpoint_interval` (5) epochs. Each
is about 200 MB, so the whole run keeps about 10 GB.

## How to run on Discover

```bash
# 1. Pack (CPU array + finalize + data preflight), then queue training:
bash scripts/submit_prepare_v4_1.sh          # SUBMIT_TRAIN=0 to pack only

# 2. Optional: loader throughput on a GPU node (before the first full run)
python -m merraflow.cli_v4_1 benchmark --workers 10 --compare-v4 4

# 3. Training continues itself (one afterok continuation per 12 h job).
#    Manual resume if needed:
RESUME=runs/merraflow_v4_1/last_v4_1.pt bash scripts/submit_v4_1.sh

# 4. Inference with a v4.1 checkpoint (v4 full-domain sampler):
python -m merraflow.cli_v4_1 predict --checkpoint runs/merraflow_v4_1/best_v4_1.pt --split test
```

The epoch log now also reports `samples/s`. The history rows add
`train_wall_s` and `samples_per_s`. When the loader keeps up, `data_wait` stays
near zero and `step` is roughly the GPU time.

## Knobs

- `packed.tile` / `packed.context_tile` control read granularity. Changing
  them requires repacking.
- `train.workers`: 10 leaves 2 cores per GPU for the trainer. Lower it if
  the node is shared.
- `train.fd_cache_size`: open packed-hour files per worker.
- Packed data is keyed to the archive, hourly-target and humidity
  fingerprints, the normalization stats, the geometry and the splits. A
  mismatch is refused, and you repack into a fresh `packed.root`.
