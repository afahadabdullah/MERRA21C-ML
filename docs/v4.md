## Data contracts and locations

Configured Discover paths, checked by preflight:

| Content | Path under `/gpfsm/dnb10/projects/p311/ML_downscaling` |
|---|---|
| Existing v2 inputs and five original targets | `data/paired_hourly_annual_v2` |
| Existing v3 hourly rainfall | `data/hwt_hourly_mean_v3_precip` |
| New HWT humidity targets | `data/hwt_q2m_v4` |

| New model, history, validation | `runs/merraflow_v4` |
| Slurm logs | `logs_v4` |

`inspect-data` reports detected hourly archive directories and verifies the
configured `index_hourly_v3_precip.json`. Each hour contains
`truth_hourly_v3_precip.npy` plus provenance. This location was identified from
`discover_v3_precip.yaml`; the local Mac does not contain the Discover archives.
Use `--hourly-targets PATH` or `HOURLY_TARGETS=PATH` if the processed directory
has moved. Multiple directories are reported, never silently substituted.

The precipitation target is `0.25 P(:00) + 0.5 P(:30) + 0.25 P(next :00)` from
HWT. This approximates an hourly mean; it is not a measured hourly accumulation.
Temperature, pressure, winds, and humidity stay at :30. This is conditional
spatial downscaling, not a lead-time forecast trained without current inputs.

The six target channels are `t2m`, `precip`, `ps`, `u10m`, `v10m`, `q2m`.
Humidity uses kg/kg internally and in NetCDF, with an initial residual unit of
0.001 kg/kg. Training-only RMS calibration subsequently scales every non-rain
residual. Generated physical humidity is clipped to [0, 1] kg/kg. Humidity input
comes from the existing `condition_v2.npy` QV2M channel; HWT humidity is used
only for supervision. Extraction validates source timestamps, grids, units,
values, and file identities. Missing high-resolution humidity stops preparation;
it is never replaced with the coarse input or zeros. If the source uses a
verified alternative variable name, change `data.humidity_target_variable`.

Previous-hour inputs append the original six dynamic predictors (PRECTOT,
U10M, V10M, TQV, QV2M, SLP) to the current local and broad-context conditions.
They use the original training-only normalization. The first hour of each
split, gaps, and hours without completed hourly rain targets are excluded.
No previous HWT truth enters the model. The frozen regression receives exactly
its original current-hour inputs, preserving its checkpoint contract.

## Training objective and capacity

V4 retains v2 conditional flow matching with Gaussian initial noise, uniform
flow times, and a quadratic velocity loss on the full patch including halos.
Rain is a full square-root field; the other channels are calibrated residuals.
The six constant channel weights are `[1, 2, 1, 1, 1, 1]`.

Half the spatial proposal is uniform; half favors coarse rainfall and coastlines
using the existing v3 input-only proposal. Sample weights remain one. This
intentionally changes the population risk toward those inputs. It does not use
truth-intensity pixel weighting. Validation uses uniform held-out patches and
reports per-field CRPS, coarse/regression MAE, ensemble-mean RMSE, bias, and
spread, plus rainfall wet fractions and false/missed wet probabilities at
0.1 mm/h. The humidity "regression" baseline is coarse QV2M because the original
regression cannot predict humidity. Best checkpoints are selected by rainfall
CRPS; check the other five variables for degradation as well.

Default model: approximately 10.5 million parameters, base 64, channel multipliers `[1,2,3,4]`, 256-dimensional time
embedding, eight attention heads, activation checkpointing. Flow weights and
optimizer start fresh. Only the original frozen v2 regression is reused.
V2/direct-precipitation/v3 checkpoints cannot resume v4.

Four GPUs × batch 8 × accumulation 2 = effective batch 64. With 32,768 samples
and 250 epochs this gives 128,000 optimizer updates, ten times the default
precipitation-only v2 run. Learning rate warms up for 2,000 updates then decays
by cosine to 5%; EMA decay is 0.9995. Settings are experiments, not guarantees
of improved skill. The checkpoint includes calibration, source fingerprints,
optimizer/scheduler, EMA, and each rank's RNG state. Resume requires the same
world size and training/data contract.

## Run on Discover

Initialize the existing environment (bash):

```bash
cd /gpfsm/dnb10/projects/p311/ML_downscaling
source /discover/nobackup/projects/GEOS_MITgcm/afahad/conda/etc/profile.d/conda.sh
conda activate /gpfsm/dnb10/projects/p311/ML_downscaling/env
export PYTHONPATH="$PWD/src"
export MPLCONFIGDIR="${TMPDIR:-/tmp}/v4-mpl-${USER}"
python -m merraflow.cli_v4 inspect-data
```

First run: prepare only the additional humidity target. This submits monthly
CPU tasks, a dependent finalizer, and four-GPU training after successful
finalization. It does not rebuild hourly rainfall:

```bash
bash scripts/submit_prepare_v4.sh
```

Set `SUBMIT_TRAIN=0` for preparation only. If preparation times out, rerun;
verified completed hours are skipped. The default CPU walltime is four hours,
so several passes may be necessary on slow storage. Jobs waiting on a failed
array are canceled by `--kill-on-invalid-dep=yes`.

Already prepared humidity:

```bash
bash scripts/submit_v4.sh
```

CPU interactive alternative (on a compute node or CPU Jupyter terminal):

```bash
python -m merraflow.cli_v4 prepare-humidity  # optionally --month 2025-12
python -m merraflow.cli_v4 finalize-humidity
python -m merraflow.cli_v4 preflight
bash scripts/submit_v4.sh
```

Train interactively in an allocation with four visible GPUs:

```bash
export OMP_NUM_THREADS=1
torchrun --standalone --nnodes=1 --nproc-per-node=4 \
  -m merraflow.cli_v4 train --config configs/discover_v4.yaml
```

Resume a stopped run:

```bash
RESUME=runs/merraflow_v4/last_v4.pt bash scripts/submit_v4.sh
```

Each scheduled training job stops after a complete epoch before its walltime
and submits one `afterok` continuation if epochs remain. Failed jobs do not
silently continue. Do not manually submit a duplicate if a continuation is
already queued. Training consumes four A100s; CPU preparation consumes none.

Optional existing data-finalizer dependency:

```bash
DEPENDENCY=JOB_ID bash scripts/submit_v4.sh
```

The submission wrapper returns the Slurm job ID without scanning archive
metadata on the login node. Preflight runs inside the training job before
`torchrun`, with phase messages for archive provenance, checkpoints, and sample
reads. This avoids scanning the verified hourly-rain and humidity sidecars
twice on shared storage. `DEPENDENCY=JOB_ID` makes the job wait for an upstream
data job; preflight then runs after that dependency succeeds. Overrides
`ENV_DIR`, `CONFIG`, `REGRESSION_CHECKPOINT`, and `HOURLY_TARGETS` propagate
through training and continuation jobs.

### Startup calibration timeout

A startup `ALLREDUCE` timeout with `NumelIn=7`, before the `V4 flow:`
message, identifies calibration's six squared-error sums and sample count.
It does not by itself distinguish a stalled data worker, uneven archive I/O,
or a GPU communication failure.

V4 explicitly starts DataLoader workers with `spawn`: forking after CUDA/NCCL
initialization can deadlock (see the
[PyTorch DDP warning](https://docs.pytorch.org/docs/stable/generated/torch.nn.parallel.DistributedDataParallel.html)).
Calibration totals now move to CPU and reduce through the existing Gloo
control group with its 12-hour timeout, so faster ranks do not leave a NCCL
operation waiting while other ranks finish archive reads. Training's NCCL
timeout is unchanged. A small distributed communication check runs before
loading archives; rank-tagged logs show that check, archive loading, calibration
progress (first batch, every 16 batches, last batch), and model setup.

After updating the code on Discover, resubmit with `bash scripts/submit_v4.sh`
if no checkpoint was produced. An empty output directory is accepted. If a
valid `last_v4.pt` exists, use the resume command above. If a rerun stalls,
compare the last progress line from each rank: a failure at the initial
communication check points to distributed startup, while a rank that stops
advancing during calibration needs data-worker/I/O or compute investigation.

## Outputs and full-domain evaluation

- Checkpoints: `runs/merraflow_v4/{last_v4,best_v4}.pt`
- Metrics over time: `runs/merraflow_v4/history.json`
- Every fifth epoch: `runs/merraflow_v4/validation_plots/epoch_0005/`
  contains `fields.png`, additional patch maps, `history.png`, `samples.npz`,
  and `metrics.json`. These are patch diagnostics for all six variables.
- Training logs: `logs_v4/train_JOBID.log`
- Humidity preparation logs: `logs_v4/humidity_ARRAYID_TASKID.log`
- Full-domain generated data: `runs/merraflow_v4/predictions/*_v4.nc`

For the February example (requires an eligible test timestamp):

```bash
python -m merraflow.cli_v4 predict \
  --checkpoint runs/merraflow_v4/best_v4.pt --split test \
  --time 2026-02-23T05:30:00 --limit 1
```

Prediction is a separate one-GPU job/interactive command, not `torchrun`.
It writes all six variables, ensemble IDs, checkpoint/source fingerprints, and
rainfall interval bounds. It blends tiled velocities at every integration
step to avoid independent tile trajectories. It is slower than patch sampling.
Use a fresh inference output directory to avoid overwriting generated members.
No real-data skill or A100 throughput has been measured by the local tests.
